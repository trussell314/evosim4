# Native engine port: progress log

Tracks the state of the TS -> Rust port. Each entry lists what's
*done* (with parity tests / commit hashes you can pull up) and what
remains. Read this when picking the port back up after a break.

The TS app on `claude/develop` is unaffected; the port lives only
under `server/`.

## Up next, in suggested order

### 1. Reaction table (~ 1-2 days)
Port `src/sim/reactions.ts` (578 lines). Sequence:
- `Reaction` struct (sChem/sCount/pChem/pCount, atpDelta, lightIn,
  vmax, uncatRate, surfaceScale, atpFloor, mrnaScale, chlScale,
  enzScale, transport).
- 26 hand-authored named reactions (respiration, ferment, beta-ox,
  photosynth, the synth-* family, digest_biop).
- Procedural-generic table built by `mulberry32(0xE2C4_BEEF)`:
  COUNT_POOL = [1,1,1,1,2,2,3,5,10], atpDelta derived from
  CHEM_BOND_POTENTIAL so reactions don't mint energy.
- 8 carbon-fix variants installed on top.
- Transport reactions in the tail (TRANSPORT_TARGETS, ...).
- RX_SLOT_* slot constants exposed.

Test against captured TS goldens for: total atpDelta sum for the
named head, sChem/pChem for the photosynth row (RX_SLOT_PHOTOSYNTH),
a sampled middle-generic row's substrate count and bond accounting.

### 2. Genome VM (~ 2-3 weeks)
Port `src/genome.ts` (1918 lines). Largest piece by far. Shape:
- Op enum + operand layout + walkGenome.
- Per-op handler signatures (`fn op_thrust(ctx: &mut VmContext)` ...).
- Bytecode interpreter loop, mutation, fission, splicing.
- Per-op profiling (count + last execution time) -- the TS has
  these; the Rust port should too.

This is the messy core; tests should compare bytecode execution
trace against the TS impl for a fixed seed.

### 3. Particle SoA store + spawn (~ 2-3 days)
Port `src/sim/core.ts` ParticleStore. Fields: x, y, z, vx, vy, vz, r,
density, chemId. SoA so the future force kernel can SIMD over
columns. Spawn loop with `spawnPosForChem`. Need region/atmosphere
constants first (small carve-out).

### 4. Force kernel: serial -> rayon -> wgpu (~ 1-2 weeks)
Port `applyParticleForcesRange` straight. Three stages:
- Serial Rust implementation; verify it matches the TS serial
  output bit-for-bit on a fixed seed.
- Rayon par-chunks at the same parallelMin threshold.
- wgpu compute kernel (literal port of `gpu-forces-shader.ts`'s WGSL;
  shaders are language-agnostic).

### 5. Collision pass (~ 1 week)
Port `src/sim/collision.ts`. SAB grid -> Rust slab; two-phase row-parity
parallel dispatch via rayon.

### 6. Creature update + chemistry (~ 2 weeks)
Port `updateCreatures` from `src/sim.ts`. Largest "messy state"
function in the codebase. Lots of branchy logic over genome ops.
Where Rust earns its keep over C++.

### 7. Region / atmosphere passes (~ 1 week)
Port `src/sim/regions.ts`, `environment.ts`, `chemolith.ts`,
`vent.ts`, etc. Pure functions over state -- straightforward but
volume-heavy.

### 8. Snapshot wiring (~ 2 days)
Have `Engine::snapshot()` actually populate the SoA blobs from the
real particle / creature stores. The blob columns are already wired
in the protocol layer (commit `f95c438`).

### 9. Save / load (~ 3 days)
Use the existing JSON save schema (SAVE_SCHEMA in TS). Reuse the
schema as the wire format; serde gets us 90% of the way there.

### 10. Controller commands (~ 1 day)
Replace the `unimplemented` Nacks in `ws.rs` with real wiring to the
engine task: SetRunning, SetSimRate, Save. The plumbing is already
there; just hook it through.

### 11. TS client adapter (~ 2-3 days)
On the TS side, swap `new Worker(...)` for a WebSocket-backed proxy
that implements the same `WorkerInbound` / `WorkerOutbound` shape.
Activated by `?server=wss://host` URL param. The existing renderer
is unchanged.

### 12. Multi-client + persistence (~ 1 week)
Phase 3 from the previous plan: session model, controller-vs-observer
roles, per-observer overlays, periodic persistence, observability
endpoints.

## Operator-facing notes

- The TS app still ships from `src/`; nothing in this port has touched
  it. The renderer keeps working as-is and the port progresses
  independently.
- After each engine subsystem lands, the determinism story is the
  same as today: serial CPU path is byte-deterministic per seed;
  parallel / GPU paths are not (PCG noise differs across the row
  partition). Goldens belong on the serial path.
- `EVOSIM_BUILD_COMMIT` ends up in the `Hello` frame, so the client
  HUD can show which engine commit it's talking to. After an admin
  update, the new commit hash is observable from the UI.

## Conventions for the port

- Every port commit should leave `cargo test`, `cargo clippy
  --all-targets -D warnings` clean.
- Constants and enum variants keep TS spelling where it doesn't
  fight Rust style (e.g. `CHEM_O2` stays uppercase). Function names
  go to snake_case.
- Goldens captured from the running TS implementation -- never
  guessed. The capture commands live in commit messages so they
  can be re-run if the TS source moves.
- New modules under `evosim_engine::*` are flat; subdirectories only
  when a clear cluster of files exists (e.g. a `chemistry/` dir if it
  ever splits into table + diffusion + ambient).
